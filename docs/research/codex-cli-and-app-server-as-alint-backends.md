# Feasibility Study: Codex CLI and app-server as alint Backends

> **Status: Superseded by a later design.** This document retains the runtime-surface research for Codex CLI, the SDK, and app-server. The architectural recommendation to extend provider types and the execution seam inside alint is no longer current. See [ACP-to-OpenAI-Compatible Gateway Design](./acp-openai-compatible-gateway.md) for the current decision: alint continues to depend only on an OpenAI-compatible interface, while an external gateway owns ACP and coding-agent lifecycles.

> Research date: 2026-08-06
>
> Validation environment: `codex-cli 0.146.0`, `@openai/codex-sdk 0.144.6`
>
> Sources: Official OpenAI Codex documentation, the official `openai/codex` source pinned to `e1831db7c31ec3ec3a88f29e95cc336858038bad`, and protocol schemas and help generated by the local CLI. No third-party material was used.

## Conclusion

Integration is feasible, and selection can continue to use `--model`. Two concepts must remain distinct: the user selects a model or inference target, while the provider configuration for that target determines whether execution uses a direct HTTP model, an ACP coding agent, or a predefined MCP agent tool.

- alint's current `ProviderDefinition` and `ResolvedProvider` describe only an `openai-compatible` HTTP endpoint and headers. Codex CLI is an agent process that manages its own authentication, model selection, context, tools, sandbox, and sessions; it does not expose an OpenAI-compatible chat endpoint.
- This does not prevent broadening the domain meaning of a provider. It can represent the execution provider for a target through a discriminated union of transports and runtimes such as `openai-compatible`, `acp-agent`, and `mcp-agent`.
- The repository already contains `@alint-js/agent-codex-cli`, which implements `AgentAdapter` through the official `@openai/codex-sdk`. It proves that Codex can run, but injecting an agent adapter into configuration in advance is not the intended final shape for `--model`-driven assembly.
- Codex should not be presented as an HTTP provider. After model resolution, the corresponding execution adapter should be assembled from the resolved provider type. The same resolved target can then carry model selection, capability matching, diagnostics, and usage attribution throughout the operation.
- An app-server adapter is justified only when alint needs a long-lived process, the complete streaming event surface, an approval UI, model discovery, or a direct bridge from `AgentTool` callbacks to Codex. `dynamicTools` remains experimental and should not be treated as a stable product contract.

ACP and MCP also occupy different protocol layers:

- ACP standardizes initialization, sessions, prompts, cancellation, updates, permissions, and session configuration between a coding-agent client and agent process. It is suitable as a general coding-agent adapter.
- MCP standardizes the discovery and invocation of tools, resources, and prompts. It can expose a coding agent, such as the Codex `codex` and `codex-reply` tools, and can expose alint `AgentTool` implementations to an ACP agent. An arbitrary MCP server, however, does not inherently provide standardized coding-agent session semantics. An `mcp-agent` configuration must therefore declare a specific tool or profile contract.

## alint's Current Provider and Model System

alint currently separates the selectable model catalog from the code that executes a model or agent, although some implicit coupling remains between these layers:

1. Setup TOML comes from global `~/.config/alint/config.toml` and project `.alint/config.toml` files. The CLI loads both and merges them by provider ID. The project layer overrides endpoint, type, and headers for a provider with the same ID, and merges same-ID models into the earlier entry. Only when the project defines no models does a selector-free call fall back to the global `default` alias.
2. Every provider must currently have `type = "openai-compatible"`, an `endpoint`, optional headers, and an array of models. A model stores its ID, name, aliases, capabilities, size, context window, and default parameters; it is not an executable client.
3. A rule calls `ctx.model(selector)`. An explicit `--model` has priority, followed by the selector string at the call site. Without an explicit request, core combines rule-level and call-site requirements for capabilities, minimum context window, size, and parameters, then selects the first matching model from the flattened registry. Size affects preference only; capabilities and context window are hard constraints.
4. `ResolvedModel` combines model metadata with provider endpoint and headers. A normal structured rule then uses `generateStructured` to call xsAI's OpenAI-compatible chat transport directly and requires one function-tool call. This execution path therefore depends on the shape of an HTTP provider.
5. An agentic rule passes the same `ResolvedModel`, prompt, and `AgentTool[]` to the `AgentAdapter` injected through configuration. The adapter is executable configuration in `alint.config.ts`; it does not belong to the setup TOML provider registry. The Apeira and Pi adapters use the resolved endpoint and model, while the Codex adapter may ignore them.

This flow shows that adding an agent-backed provider involves more than another enum member. The TOML schema, resolved-provider union, provider probe and benchmark, execution dispatch, setup UI, and usage attribution must change together. The concept remains valid; the required refactor concerns agent assembly timing and a unified execution seam, not the removal of `--model` or the provider registry.

A more suitable internal shape would be:

```ts
interface InferenceExecutor {
  execute: (request: InferenceRequest) => Promise<InferenceResult>
}

type ProviderDefinition
  = | AcpAgentProvider
    | McpAgentProvider
    | OpenAICompatibleProvider

interface ResolvedInferenceTarget {
  model: ResolvedModelMetadata
  provider: ResolvedProvider
}
```

`--model` and `ctx.model()` would only resolve a `ResolvedInferenceTarget`. Core would then select an executor adapter from `provider.type`; the rule would not need to know whether xsAI, an ACP subprocess, or an MCP tool performs the work. The existing `AgentAdapter` could become an implementation detail of an executor instead of a global configuration injection independent of model selection.

## Comparison of Three Integration Surfaces

| Integration surface | Capabilities and costs | Fit with alint | Recommendation |
| --- | --- | --- | --- |
| Direct `codex exec --json` | Starts a subprocess per invocation; reads input from stdin, emits JSONL on stdout, and reports progress or errors on stderr; supports schemas, session resume, and ephemeral sessions | Can implement an adapter, but alint must track the JSONL protocol and CLI changes | Do not duplicate this work; use the official TypeScript SDK |
| `@openai/codex-sdk` | Requires Node 18+; officially wraps `codex exec` and JSONL; provides `run`, `runStreamed`, `AbortSignal`, `outputSchema`, usage, and thread resume | Closely matches `AgentAdapter(request) -> {answer, usage}`, but cannot call in-process alint `AgentTool` callbacks | **Current recommendation** |
| `codex app-server` | Long-lived bidirectional JSON-RPC; thread, turn, and item lifecycles; approvals, authentication, model list, detailed errors, and tool callbacks | Can provide `AgentTool`, model discovery, and persistent connections, but requires a custom JSON-RPC client, routing, approval handling, retries, and version/schema upgrades | Use as a second phase only when these capabilities are required |

OpenAI defines the TypeScript SDK as a wrapper around the CLI: it spawns `@openai/codex`, exchanges JSONL over stdin and stdout, and requires Node.js 18 or later. [Official SDK README](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/README.md#L1-L13)

## CLI and SDK Path

### Non-interactive protocol

`codex exec --json` turns stdout into a JSONL event stream. Typical events include `thread.started`, `turn.started`, `item.*`, `turn.completed`, `turn.failed`, and `error`. `turn.completed` includes input, cached-input, output, and reasoning token usage. The CLI also supports `--output-schema FILE`, `--output-last-message FILE`, `--ephemeral`, `resume`, and reading the prompt from stdin. [Official non-interactive documentation](https://developers.openai.com/codex/noninteractive) [CLI argument source](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/exec/src/cli.rs#L22-L65)

The TypeScript SDK always starts the CLI with `exec --experimental-json`. The current CLI retains that name as an alias for `--json`. alint should not depend on the old flag itself; the SDK should own protocol compatibility. [SDK startup and argument mapping](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/src/exec.ts#L80-L181) [CLI alias](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/exec/src/cli.rs#L56-L64)

### Authentication reuse

`codex exec` reuses stored CLI authentication by default. Automation can set `CODEX_API_KEY` for a single execution; the official documentation states that this environment variable is supported only by `codex exec`. For local alint use, the minimum configuration inherits the current process environment and `CODEX_HOME` without reading, copying, or printing `auth.json`. [Official authentication documentation](https://developers.openai.com/codex/noninteractive#authenticate-in-automation)

The SDK inherits the Node process environment by default. If `env` is supplied, it replaces `process.env` completely before the SDK adds required variables and the explicit `apiKey -> CODEX_API_KEY` mapping. The `env` option is therefore a complete environment, not a partial patch; an incorrect value can remove `PATH`, proxy variables, or `CODEX_HOME`. [SDK environment documentation](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/README.md#L119-L138) [SDK environment implementation](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/src/exec.ts#L155-L181)

### Structured output

Both the CLI's `--output-schema` and SDK's `thread.run(input, { outputSchema })` constrain the final agent message. The SDK writes the schema to a temporary file, passes the file to the CLI, and removes it afterward. [Official SDK structured-output documentation](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/README.md#L51-L83) [SDK turn implementation](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/src/thread.ts#L68-L115)

The existing `createCodexCliAdapter({ outputSchema })` can set one fixed schema for every request, but `AgentRequest` has no per-request schema field. If alint needs different rules to provide different output schemas, schema should first become part of the common agent contract instead of a rule-specific branch in the Codex adapter.

### Cancellation, timeouts, errors, and usage

- SDK `TurnOptions.signal` passes directly to Node `spawn(..., { signal })`, allowing an alint run or rule timeout to cancel the subprocess. The SDK has no separate `timeoutMs` option. [SDK abort implementation](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/src/exec.ts#L181-L232)
- `run()` converts a JSONL `turn.failed` event into a thrown `Error`. A non-zero CLI exit or signal termination also throws and includes captured stderr. [SDK turn-error mapping](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/src/thread.ts#L116-L139) [SDK process-error mapping](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/src/exec.ts#L186-L235)
- SDK usage includes input, cached-input, output, and reasoning-output tokens. The existing adapter maps only input and output, with `totalTokens = input + output`; the current alint `AgentUsage` also has no cached or reasoning fields. This supports basic accounting but does not preserve Codex's complete billing and reasoning breakdown. [SDK usage events](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/README.md#L32-L49)

### Concurrency

The SDK has no connection pool or global concurrency controller. Every `run` spawns a `codex exec` process. The alint scheduler can therefore invoke it concurrently, but the limit should be explicit and specific to the Codex runtime instead of reusing assumptions for HTTP-provider gateway concurrency. Process count, repository file contention, MCP processes, and account rate limits all matter. The ability to spawn multiple processes does not constitute an OpenAI guarantee for arbitrary concurrency. [SDK process startup for each run](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/sdk/typescript/src/exec.ts#L80-L209)

## app-server Path

### Protocol and lifecycle

app-server uses bidirectional JSON-RPC 2.0, with `jsonrpc: "2.0"` omitted on the wire. Its default local transport is JSONL over stdio. WebSocket is explicitly experimental and unsupported and should not be used for an alint production integration. [Official app-server protocol source documentation](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L20-L58)

The minimum lifecycle for one connection is:

1. Send `initialize` once, then send `initialized` after receiving the response. Requests sent earlier are rejected, as is a repeated initialization.
2. Call `thread/start` or `thread/resume` and retain `thread.id`. An independent alint lint job can use `ephemeral: true` to avoid adding entries to the user's session history.
3. Call `turn/start` and consume the `turn/started` and `item/*` streams.
4. Treat `turn/completed` as terminal; its status is completed, interrupted, or failed.

[Official lifecycle](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L69-L95) [Turn events](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L1519-L1531)

### Schema and version boundaries

`codex app-server generate-ts --out DIR` and `generate-json-schema` produce types and schemas that match the current CLI version exactly. Generated output excludes experimental APIs by default and includes them only with an explicit `--experimental`. [Official schema-generation instructions](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L59-L64) [Stable and experimental generation boundary](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L2382-L2434)

An implementation should pin the `@openai/codex` or CLI version, generate stable-only TypeScript bindings from that version, and treat “upgrade CLI + regenerate + typecheck + protocol tests” as one change. It should not handwrite the large protocol union or expose `--experimental` output to alint users by default.

### `model/list`, model overrides, and the alint model registry

The stable app-server interface provides `model/list`, which returns available models, visibility state, supported reasoning efforts, and upgrade information. `thread/start` and `turn/start` also accept model overrides. [Official interface list](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L223-L234) [Turn model override](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L840-L885)

`model/list` is the runtime catalog under the current Codex authentication and configuration; it is not equivalent to `/models` on an OpenAI-compatible provider. It can support Codex-adapter configuration UI and validation, but should not be written unconditionally into the general alint provider registry. Doing so would conflate model capabilities, authentication ownership, and endpoint ownership.

### `outputSchema`

`turn/start.outputSchema` is an optional JSON Schema for the current turn and does not become a sticky setting for later turns. This maps directly to alint's semantics of requesting one structured result for each rule invocation. [Official turn example](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L830-L885)

### `dynamicTools` and alint `AgentTool`

app-server is currently the only Codex path that can directly bridge alint `AgentTool.execute`. A client registers schemas in `thread/start.dynamicTools`. When Codex invokes one, app-server sends the client an `item/tool/call` request; alint executes the callback and responds with `contentItems` and `success`. [Official dynamic-tools protocol](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L1726-L1783)

The limitation is that this interface is explicitly experimental. Initialization must set `capabilities.experimentalApi = true`, and experimental APIs have no backward-compatibility guarantee. Therefore:

- The existing `@alint-js/agent-codex-cli` correctly fails fast on a non-empty `request.tools`; the official TypeScript SDK has no in-process callback surface for these tools.
- An app-server adapter can be a separate package, but its name, README, and configuration should explicitly identify an experimental tools bridge. It must not silently fall back or claim full equivalence with other adapters.

### Concurrency, backpressure, timeouts, and errors

- The app-server ingress, processing, and outbound queues are bounded. Under overload it returns JSON-RPC `-32001` with `Server overloaded; retry later.`, and the official contract requires exponential backoff with jitter. [Official backpressure contract](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L51-L56)
- Active turns on one thread must be scheduled according to the protocol. Cancellation uses `turn/interrupt`, and the final `turn/completed(status: interrupted)` is the confirmation; the job must not be released merely because the RPC returned. [Official interrupt contract](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L1087-L1101)
- Turn errors appear as `error` events and as `message`, `codexErrorInfo`, and `additionalDetails` on a failed `turn/completed`. Official categories include context-window, session-budget, usage-limit, HTTP or stream, unauthorized, sandbox, and internal errors. [app-server error categories](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L1590-L1613)
- Token usage streams through `thread/tokenUsage/updated`, while `turn/completed` remains the terminal event. [Official usage event](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L1519-L1526)

The app-server CLI subcommand itself remains marked `[experimental]`, while its protocol separately distinguishes a stable default surface from an opt-in experimental surface. These layers do not mean that the entire protocol is stable, nor that every interface is unusable. [CLI experimental marker](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/cli/src/main.rs#L149-L155) [Stable and experimental protocol layers](https://github.com/openai/codex/blob/e1831db7c31ec3ec3a88f29e95cc336858038bad/codex-rs/app-server/README.md#L2382-L2434)

## Evaluation of the Existing `@alint-js/agent-codex-cli`

The existing implementation has the right layering direction:

- It uses the official SDK instead of a handwritten JSONL parser.
- Codex can use its local model configuration, or receive the alint model ID through `useRequestModel: true`.
- It passes `request.signal` to the SDK and maps token usage back to alint.
- It fails fast for `AgentTool` instead of pretending to support it.
- It creates a new thread by default and does not implicitly share conversational context across lint requests.

The following product boundaries still need explicit decisions:

1. It is currently a standalone agent adapter, not a provider adapter driven by model resolution in setup TOML. This describes the current implementation, not a constraint on the target architecture.
2. `AgentRequest.model` is always a model resolved from the alint registry, and existing rules attribute usage to its ID and provider. By default, the adapter does not pass it to Codex. The runtime model may therefore come from Codex `config.toml`, while diagnostics and usage are attributed to another alint model. Before formal support, choose one policy: require `useRequestModel` by default and validate provider consistency, or have `AgentResult` return the actual runtime model and provider for accounting. Passing only a model ID still does not pass the alint endpoint or headers to Codex.
3. The repository's primary agentic rules pass non-empty `AgentTool[]`, including required `submit_review` or reporting callbacks. The existing adapter rejects them. It is therefore suitable only for custom agent rules that do not use alint tools and cannot directly replace Apeira or Pi for these rules.
4. The recommended default sandbox is `read-only`. Linting should not permit worktree changes merely because Codex has agent capabilities.
5. Codex needs a runtime-specific concurrency limit; it should not be an alias for ordinary HTTP-provider concurrency.
6. If per-rule schemas are required, evolve the `AgentRequest` contract first.
7. Validate SDK and CLI versions together. The official SDK sends the flags and expects the events for its CLI version; do not casually replace it with a different major version through `codexPath`.

## Recommended Evolution Sequence

1. **Establish one execution seam first:** let `ResolvedInferenceTarget.provider.type` select the executor adapter instead of injecting one global `agent` in advance.
2. **Make providers a discriminated union:** retain `openai-compatible` and add an ACP agent. An MCP agent must bind to a specific coding-agent tool or profile contract; an arbitrary MCP server is not an agent.
3. **Use ACP first for the general coding-agent path:** ACP already covers session lifecycle, cancellation, updates, permissions, and session configuration. It also lets the client provide alint tools as MCP servers when creating a session.
4. **Treat the existing Codex SDK adapter as migration evidence and a Codex-specific implementation:** default to read-only and resolve actual model attribution first. Codex can also enter through ACP via `codex-acp`, or through stable MCP `codex` and `codex-reply` tools from `codex mcp-server`.
5. **Measure before setting concurrency defaults:** use real repositories to measure cold start, average turn duration, memory, MCP subprocesses, and rate-limit errors before selecting runtime concurrency.
6. **Prototype a native app-server adapter only for a concrete requirement:** use local stdio, pin the CLI, and generate only stable schemas. Implement thread, turn, `outputSchema`, `model/list`, error, and interrupt handling before evaluating experimental `dynamicTools` separately.
7. **Do not use WebSocket as the default deployment:** the official project explicitly marks it experimental and unsupported.
